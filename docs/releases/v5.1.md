# Release Notes — v5.1 (unreleased)

**Base:** `master` + mr-deed adapter P1 (issue [#265](https://github.com/pandazxx/codex-slack/issues/265), PR [#270](https://github.com/pandazxx/codex-slack/pull/270))
**Preceded by:** v5.0

---

## Summary

v5.1 adds **mr-deed** as a third staff adapter, alongside `claude-code` and `codex`. A mr-deed staff runs [mr-deed](https://github.com/pandazxx/mr-deed) `v0.1.0` in-process on the agent worker, using `bash` in the topic worktree. It streams to the chat like the other adapters and keeps its session across turns.

This release adds the first Alembic revision after the v5.0 baseline. **Existing installs refuse to start until the schema is migrated** (see the upgrade steps below).

---

## What changed

### mr-deed adapter

- New staff adapter value `mr-deed`. In the staff form, `Sub-agent` names the mr-deed config (blank = `default`). An optional **mr-deed Config** YAML (`agent_config`) is used as-is instead of a named config. `Model` sets the litellm model id, and `System Prompt` is appended to the config's system template as literal text.
- Config resolution: the staff's `agent_config`, then a shipped `config/mr-deed/<name>.yaml`, then mr-deed built-ins. Shipped configs:
  - `default`: tool-call, at most 100 steps and $3.00 per turn.
  - `ollama`: for local models (`ollama_chat/<model>` with the `OLLAMA_API_BASE` config variable), $0-cost aware, at most 50 steps per turn.
  See the user manual, "Local models (Ollama)".
- Runs in a local environment rooted at the topic worktree. Per-turn values (dispatch token, task depth, topic) go to that turn only, never the worker's process environment.
- Sessions are stored as mr-deed trajectories on a new per-workspace volume `codex-mrdeed-{workspace_id}` (`/home/appuser/.mr-deed/sessions/`) and resumed on the next turn. A staff's session scope applies as usual; `none` keeps nothing.
- Every way a turn can end has a named reply: limit hit, timeout, repeated format errors, cancelled, model call failed, crashed, config invalid, session file unreadable, or session directory not writable. Cancel and the stale-stream check work as for the other adapters.
- **Credentials:** mr-deed uses litellm, so it needs a real provider API key (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`, …) via the existing config variables. Codex `auth.json` and Claude subscription logins do not work.
- Not yet supported: codex-slack tools for mr-deed (orchestration / notes; planned), and project configs under `.prj_assistant/mr-deed/` (planned).

### Database

- Alembic revision `000000000002` adds the nullable `staffs.agent_config` column. Existing staffs are unaffected.
- Pre-baseline SQLite installs are now upgraded to head after being stamped at the baseline, instead of stopping at the baseline.

## Upgrade steps for existing installs

Installs on v5.0 are at revision `000000000001`. After deploying v5.1, master logs `DB schema is behind code` and refuses to start. Then:

1. Snapshot and migrate: `just migrate <env> <tag>` (prod needs `confirm=yes`: `just migrate prod <tag> confirm=yes`). It runs from the `<tag>` image, stops master if it is running or crash-looping, takes a snapshot, migrates, and never starts master. It is idempotent: if the database is already at head it exits 0 and changes nothing.
2. Deploy: `just deploy <env> <tag>`.

If you deploy first, `just deploy` fails its healthcheck and prints `→ run: just migrate <env> <tag>`; run that, then deploy again.

Fallback if the recipe is unavailable: the manual `run --rm --no-deps` procedure in `.sre/operations/db-snapshot-migrate.md` (`scripts/db.sh snapshot-and-migrate`), then restart master.

Agent containers pick up the new `codex-mrdeed-{workspace_id}` volume the next time master spawns them; no manual step is needed.

Rollback: the migration only adds a nullable column. Running v5.0 against a migrated DB is refused as "ahead", so to roll back, downgrade one revision (`alembic downgrade 000000000001`) before redeploying v5.0, or restore the snapshot taken in step 1.

## Known issues

- `scripts/db.sh verify-schema` always exits 1 (`DRIFT DETECTED: … env.py does not provide a MetaData object`): it runs `alembic check`, but `alembic/env.py` passes `target_metadata=None`. This predates v5.1. Use `SELECT version_num FROM alembic_version` to confirm the revision instead (`just migrate` does this for you and prints the revision before and after).
