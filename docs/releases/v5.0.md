## Summary

v5.0 switches the default database to **PostgreSQL**. Existing installs that relied on the implicit SQLite default will not start until they either set `DATABASE_URL` explicitly (to keep SQLite) or migrate to Postgres. All existing data is preserved in the SQLite file, which is never modified by this upgrade.

SQLite remains supported as an opt-in alternative (set `DATABASE_URL` to a `sqlite+pysqlite://` URL). MySQL support is deferred; the dialect code paths remain in the codebase but are untested and unsupported. Master refuses to start if `DATABASE_URL` uses a `mysql` scheme. See [ADR-0020](../decisions/0020-mysql-support-details.md).

## What changed

### Postgres is the default

When `DATABASE_URL` is unset and no `master_data.db` is found, master connects to `postgresql+psycopg://master:<POSTGRES_PASSWORD>@postgres:5432/master`. The bundled `postgres:17-alpine` service is started alongside master when `COMPOSE_PROFILES=db-bundled` is active.

A new `docker-compose.postgres.yml` overlay declares the `postgres` service (behind the `db-bundled` profile) and passes the DB configuration into master. The `justfile` includes this overlay in every `dev-up`, `deploy`, and `undeploy` invocation automatically.

### Startup migration state machine

`startup_db()` runs on every master start:

- **Empty DB** — runs `alembic upgrade head` automatically, then starts.
- **Up-to-date** — starts immediately.
- **DB behind code** — exits 1 with `ERROR: DB schema is behind code (DB=…, code=…). Run \`scripts/db.sh migrate\` …`
- **DB ahead of code** — exits 1, points at a likely accidental downgrade.
- **Pre-baseline SQLite** (existing installs upgraded from v4.x or earlier without Alembic) — applies pre-baseline fixups in-place and stamps the baseline; no operator action required for the SQLite path.

### SQLite-upgrade safety net

If `DATABASE_URL` is unset and a non-empty `master_data.db` with a `workspaces` table exists under `MASTER_DATA_DIR`, master exits 1 immediately with an actionable message. It never silently switches to Postgres while SQLite data is present.

### Snapshot and migration tooling

`scripts/db.sh` provides provider-neutral export/import:

```
scripts/db.sh snapshot export    --source-url URL --out DIR
scripts/db.sh snapshot import    --in DIR --target-url URL [--yes] [--lock-timeout 30s]
scripts/db.sh snapshot-and-migrate [--source-url URL] [--target-url URL] [--out DIR]
scripts/db.sh migrate
scripts/db.sh verify-schema
```

Snapshots are a directory of JSONL files (one per table) plus a `manifest.json` with SHA-256 checksums, schema version, row counts, and source dialect. Type normalisation on export ensures booleans, JSON columns, and floats round-trip correctly across dialects.

### Database schema managed by Alembic

The previous in-code `_SCHEMA` string and `_MIGRATIONS` list are replaced by Alembic migrations. The baseline revision (`000000000001`) captures the current schema using `op.create_table()` with typed Core columns, making it portable across SQLite and Postgres.

### CI matrix expanded

Every PR now runs the test suite against SQLite and Postgres; both gate merge. The MySQL CI job is disabled (`if: false` in `ci.yml`). A round-trip test (SQLite → export → import → Postgres) verifies sequence reset and row equality.

### New configuration variables

See [`docs/references/config.md`](../references/config.md) § Database for the full reference.

| Variable | Description |
|---|---|
| `DATABASE_URL` | SQLAlchemy URL; overrides all other DB config when set. |
| `POSTGRES_PASSWORD` | Password for the bundled Postgres; required when `DATABASE_URL` is unset. |
| `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_DB` | Bundled URL components; defaults: `postgres`, `5432`, `master`, `master`. |
| `DB_POOL_SIZE` | SQLAlchemy `pool_size`; default `5`; ignored for SQLite. |
| `DB_POOL_MAX_OVERFLOW` | SQLAlchemy `max_overflow`; default `10`; ignored for SQLite. |
| `DB_ECHO_SQL` | Log every SQL statement; off by default. |
| `COMPOSE_PROFILES` | Set to `db-bundled` to start the bundled Postgres service. |

## Breaking change — upgrade steps for existing installs

**Existing installs will refuse to start until you take one of the following actions.**

### Option A — Keep SQLite (zero downtime, zero data migration)

Add to `.env` or set in the container environment:

```
DATABASE_URL=sqlite+pysqlite:////opt/codex-slack/data/master/master_data.db
```

Then start master normally. This opts out of Postgres entirely; the SQLite file is used as before.

### Option B — Migrate to Postgres (recommended for new and production installs)

**One-command migration** (when master is not running):

```bash
SQLITE_URL='sqlite+pysqlite:////opt/codex-slack/data/master/master_data.db'
PGPW="$(openssl rand -hex 24)"

# 1. Add to .env
echo "COMPOSE_PROFILES=db-bundled" >> .env
echo "POSTGRES_PASSWORD=${PGPW}" >> .env

# 2. Start Postgres
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d postgres

# 3. Migrate
docker compose -f docker-compose.yml -f docker-compose.postgres.yml \
  run --rm --no-deps \
  -e "DATABASE_URL=${SQLITE_URL}" \
  master bash scripts/db.sh snapshot-and-migrate \
    --source-url "${SQLITE_URL}" \
    --target-url "postgresql+psycopg://master:${PGPW}@postgres:5432/master"

# 4. Point master at Postgres
echo "DATABASE_URL=postgresql+psycopg://master:${PGPW}@postgres:5432/master" >> .env

# 5. Start master
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d
```

For the SRE-managed staging cut-over, see `.sre/operations/deploy.md` § "Staging cut-over: SQLite to bundled Postgres".

Full procedure with verification and rollback: [`docs/guides/runbooks/migrate-sqlite-to-postgres.md`](../guides/runbooks/migrate-sqlite-to-postgres.md).

**Rollback** (SQLite data is untouched — migration never writes to the source):

```
DATABASE_URL=sqlite+pysqlite:////opt/codex-slack/data/master/master_data.db
```

Set that in `.env` and restart. Postgres data from after the migration is discarded.

## M0 (v5.0-rc1)

M0 is the groundwork PR that preceded this release:

- Introduced `src/master/db/` package with SQLAlchemy Core engine and a backward-compatible `get_connection()` shim.
- Converted all 16 production modules and 13 test modules from qmark `?` to `text()` with named `:param` bindings.
- Funnelled all direct `sqlite3.connect()` calls through the shared engine.
- Added `scripts/db.sh` scaffold and `alembic/` with the baseline revision.
- No user-visible change in M0; all tests passed on SQLite.

## Notes

MySQL support was deferred after this release was cut. The MySQL CI job is disabled (`if: false`) and master refuses to start if `DATABASE_URL` uses the `mysql` scheme. The supported providers are Postgres (default) and SQLite (opt-in). See [ADR-0020](../decisions/0020-mysql-support-details.md).

## Fixed during the RC cycle

- **rc2 → rc3:** the snapshot tool could "migrate" an empty DB when the SQLite file wasn't visible in the container (for example, the wrong compose project). It now opens SQLite sources read-only, refuses missing, empty or pre-baseline sources, records the source's real schema revision, and prints per-table row counts. `scripts/db.sh migrate` now upgrades legacy SQLite files.
- **rc3 → rc4:** "Recent Topics" was empty on Postgres, and stale-stream cleanup was silently broken. Both were caused by `GROUP BY` queries that only SQLite accepts.
- **rc4 → rc5:** Postgres test-coverage gap closed ([#274](https://github.com/pandazxx/codex-slack/pull/274)). Tests no longer silently run on SQLite in the Postgres CI leg; a sqlite3 lint and a route-coverage guard enforce this.
- **rc5 → rc6:** MySQL support deferred ([#281](https://github.com/pandazxx/codex-slack/pull/281)). Master and `scripts/db.sh` refuse `mysql`/`mariadb` URLs with a pointer to ADR-0020.
